# NON_GOALS.md — 不可突破的边界

> 每条都附有"重新考虑的条件"。任何想突破此清单的 PR 必须先修改本文件并经过明确审批。
> 创建于 2026-06-21，基于 v8.0 三次崩溃的教训。

---

## 1. 不做多 Agent / Mesh / 工作流编排

**原因**: v8.0 的 mesh 模块（21% 测试通过率）是崩溃的主要贡献者。多 Agent 引入的协调复杂度远超单 Agent 的执行复杂度。

**重新考虑条件**: 单 Agent 执行循环连续 3 个月零生产故障，且有具体场景（附复现步骤）证明单 Agent 在语义上无法表达该需求。

---

## 2. 不做向量库 / 知识图谱 / 语义检索

**原因**: v8.0 的检索治理层（Phase 3）引入 Python + TS 双语言栈，导致类型系统分裂。项目记忆用结构化 JSON + append-only 足够。

**重新考虑条件**: 项目记忆条目超过 10,000 条，且 `recentTasks/recentDecisions` 的 O(N) 遍历成为实测瓶颈（附 profile 数据）。

---

## 3. 不做预算 / 成本追踪 / Token 计费

**原因**: v8.0 的 Token Budget 系统本身成为新的复杂度来源——预算计算比执行还复杂。终止条件（maxTurns/maxContext/maxRetries）是确定性的，预算不是。

**重新考虑条件**: 终止条件系统运行 6 个月，出现 3 次以上"因终止条件过早截断导致任务失败"且有数据证明预算感知能避免。

---

## 4. 不做自动演化 / 自我升级 / Schema 自动迁移

**原因**: v8.0-clean 的类型重构（366 编译错误）就是"自动迁移"的失败案例。Schema 变更必须人工审计。

**重新考虑条件**: Schema 版本连续 12 个月未变更，且有 3 个以上外部项目依赖 AIOS Schema 的稳定 API。

---

## 5. 不做云调度 / 分布式执行

**原因**: v8.0 的 transport + infrastructure 层（0 运行实例）是最典型的"先建后用"废墟。单机执行是 AIOS 的核心价值。

**重新考虑条件**: 单 Agent 在单机上连续运行 30 天零故障，且有具体场景（附延迟/吞吐数据）证明单机无法满足。

---

## 6. 不做复杂权限体系 (L1/L2/L3)

**原因**: v8.0 的三级权限审批流从未完整实现，且 AUTO/MANUAL 两级已被 aios-core 验证足够。

**重新考虑条件**: AUTO/MANUAL 两级审批运行 6 个月，出现 5 次以上"因审批粒度不足导致误放行"的安全事件。

---

## 7. 不在 Charter 目录结构外新增顶层目录

**原因**: v8.0 从 4 个顶层目录膨胀到 14 个，每次新增"看起来无害"，累积后不可逆。Charter §2 冻结了目录。

**重新考虑条件**: 无。这是不可协商的。如果需要新目录，先改 Charter 并走 MANUAL 审批。
