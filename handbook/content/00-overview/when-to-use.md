# 选择使用方式：Web、CLI、SDK 还是插件

## 快速选择

| 你的目标 | 首选入口 | 原因 |
| --- | --- | --- |
| 人工探索一个仓库 | Web UI | 可以看到工作区、审批和会话状态 |
| 给一次任务并拿退出码 | Headless CLI | 适合脚本和简单流水线 |
| 在 Python 程序里管理多次运行 | Python SDK | 可以接管 cwd、session、结果和日志 |
| 让团队固定一套运行时 | 自定义 profile/bundle | 将工具、Provider 和权限组合固定下来 |
| 增加模型、工具或界面能力 | 插件 | 使用 dsh 的扩展 seam，而不是改核心循环 |
| 只问一个事实，不需要工具 | 普通模型 API | 运行面更小，配置更简单 |

## Web UI 适合人工闭环

Web UI 的强项不是“更聪明”，而是把人放在任务边界上：

- 人可以先确认 workspace；
- Provider 和模型可以在设置页选择；
- 需要批准的工具动作可以停下来询问；
- session 历史和当前工作可以一起查看；
- 任务失败时可以暂停而不是让流水线自动继续。

它更适合第一次运行、需要看清代理行为、或任务范围会随着观察结果调整的场景。

## Headless 适合确定性入口

Headless 适合：

- 任务文本固定；
- workspace 可自动创建；
- 验收命令可由脚本执行；
- 失败可以通过退出码阻断流程；
- 不需要每一步都由人点确认。

它不适合把不可信的 Issue 原文直接变成有写权限的指令。外部输入要先经过范围、权限和注入风险处理。

## Python SDK 适合程序控制

SDK 适合需要：

- 把 session ID 存进自己的任务数据库；
- 将结果、事件和异常映射到业务状态；
- 为每个任务创建隔离工作区；
- 控制重试、超时和并发；
- 把 dsh 作为更大流程中的一个阶段。

SDK 不会自动替你解决隔离和验收。尤其是官方示例使用较宽的本地执行能力时，必须先把它放进临时 checkout 或容器。

## 插件适合改变系统能力

如果只是想给模型一段额外说明，先写清楚任务文本或系统提示词；如果要新增工具、模型适配器、事件策略、存储后端或 UI 节点，才考虑插件。

插件化的好处是能力边界可组合、可卸载、可替换；代价是需要理解 profile、bundle、Cordis context、事件分发和生命周期。插件开发章节会把这些概念拆开说明。

## 不适合使用 dsh 的情况

以下任务通常不该直接交给 Agent：

- 没有可恢复副本的生产目录；
- 需要百分之百确定性且不能人工复核的不可逆操作；
- 包含大量未分类秘密或受监管数据；
- 验收标准只能靠“看起来合理”判断；
- 需要的模型、Provider 或插件版本尚未固定；
- 任务边界会随着外部网页内容任意扩大。

先降低任务范围，或者换成普通脚本、静态分析器和人工审批流程。
