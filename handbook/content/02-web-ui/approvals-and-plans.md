# 计划、审批、拒绝与中断

## 计划不是权限

Agent 可能先给出计划，或使用计划工具组织工作。计划回答“打算做什么”，权限回答“哪些动作可以发生”，审批回答“这一次动作是否允许”。

三者关系如下：

~~~text
任务契约：允许做什么、怎样算完成
  ↓
权限/沙箱：进程实际上能做什么
  ↓
计划：Agent 选择怎样完成
  ↓
审批：人是否放行当前高影响动作
  ↓
工具执行：实际发生了什么
~~~

计划写得合理，不代表后续命令安全。审批通过，也不代表输出已经验收。

## 什么时候应该批准

批准前至少看四件事：

1. 工具名称和参数；
2. 目标路径或命令的影响范围；
3. 是否包含外部输入、密钥或不可逆操作；
4. 执行后如何检查和回滚。

对小范围代码修改，批准一次明确的编辑和测试可以接受；对递归删除、生产写入、安装未知依赖、上传数据或修改权限，应该停止并重新定义任务。

## 什么时候应该拒绝

遇到以下情况直接拒绝或暂停：

- workspace 不是任务约定的目录；
- 命令把变量、路径或输入展开到未知范围；
- 请求访问 .env、私钥、凭据文件或客户数据；
- 只读任务突然要写文件；
- 任务要求联网，但契约没有允许；
- 代理声称必须启用最高权限，却没有说明具体动作；
- 验收方式仍然不明确。

拒绝不是让模型“没法工作”，而是把控制权留在边界上。拒绝后可以要求它提出低风险替代方案。

## 审批中的命令检查

不要只看命令开头。逐项检查：

- shell 是否解释了通配符、重定向、管道和命令替换；
- 当前目录是否就是目标 workspace；
- 参数中是否有复制粘贴的网页内容；
- 是否会下载并执行代码；
- 是否会修改依赖锁文件；
- 是否会把文件内容发送给外部服务；
- 是否会启动后台任务而你无法看到结果。

## 中断和暂停

当任务偏离范围时，先暂停，再保存上下文：

~~~text
已完成：
已观察：
已产生的改动：
当前 session：
最后一条成功验证：
未完成：
下一步需要的权限：
~~~

不要在不知道当前工具是否仍在运行时直接关闭终端。对后台任务，先查询或停止对应任务，再检查进程和工作区。

## 人工审批的最低标准

审批界面只能告诉你当前请求，不一定告诉你整个任务是否正确。因此审批人应有：

- 任务目标和禁止事项；
- workspace 和基线 diff；
- 当前模型与 Provider；
- 权限和沙箱；
- 回滚命令；
- 外部验收命令。

没有这些上下文时，最安全的动作是拒绝并要求任务补全，而不是盲目批准。
