# Web UI 首次任务：从零到第一份结果

## 目标

这一章的目标不是让代理完成复杂开发，而是确认四条链路：

~~~text
服务可访问
  → 模型可用
  → workspace 正确
  → 只读任务可以被检查
~~~

每一步都能单独停下来。

## 第一步：启动服务

~~~bash
npx @deepseek-ai/dsh web
~~~

启动后记录终端显示的本机地址。另开终端检查端口时，只检查本机：

~~~bash
curl -I http://127.0.0.1:3080
~~~

如果端口被占用，使用当前版本支持的端口参数，并确认浏览器打开的是新的地址。

## 第二步：配置模型

进入 Settings → Models，先配置一个最简单的 Provider。不要一开始同时添加多个自定义端点，因为出错时难以知道请求走了哪条路。

检查：

- Provider ID 是否稳定；
- 模型 ID 是否真实存在；
- 凭据是否通过设置页或环境变量引用；
- 当前 endpoint 是否允许从这台机器访问；
- 模型的输入模态是否满足任务。

不要用打印密钥来确认配置。若出现 MISSING_CREDENTIAL，先看凭据引用和环境变量名；若出现 UNKNOWN_MODEL，先看 Provider 保存状态和模型 ID。

## 第三步：准备 workspace

选择一个干净的 checkout 或可删除副本。进入选择工作区界面后，添加项目目录并选中。

在终端保存基线：

~~~bash
git status --short
git diff --stat
~~~

如果有未提交改动，先记录它们属于谁。只读任务不应让基线发生变化；写入任务需要另建临时分支或副本。

## 第四步：发送第一条任务

先使用只读请求：

~~~text
目标：总结当前仓库的主要目录、关键包和测试入口。
范围：只读取当前选中的 workspace。
禁止：不要创建、修改或删除文件；不要安装依赖；不要联网；不要访问 workspace 之外的路径。
要求：每个重要结论列出文件依据；区分观察、推断和不确定项。
停止：需要写入、安装、联网或提高权限时先停下来询问。
~~~

这不是 dsh 的特殊语法，而是把任务边界写清楚的提示模板。

## 第五步：检查代理行为

任务结束后，不要只读最终回答。检查：

1. 页面显示的 workspace；
2. 工具调用和审批请求；
3. 回答引用的文件是否真的存在；
4. 命令输出是否与结论一致；
5. 工作区 diff 是否保持预期。

~~~bash
git status --short
git diff --check
~~~

如果只读任务出现任何 diff，先不要清理，先判断哪个动作产生了它。

## 第一轮成功的定义

“成功”至少包括：

- 服务可访问；
- Provider 和模型可选；
- workspace 选对；
- 任务完成或明确停止；
- 无未预期的敏感信息外泄；
- 工作区状态与任务契约一致。

它不要求第一轮就证明长任务恢复、插件兼容或模型质量。那些是后续章节的独立问题。
