# 远程与团队使用 Web UI

## 本机服务与共享服务不是一回事

默认本机地址适合个人使用。把 Web UI 绑定到局域网或公网，会额外引入：

- 谁能访问页面；
- 谁能选择哪些 workspace；
- 谁能看到 session 和日志；
- 浏览器到 dsh 的网络路径；
- dsh 到 Provider 的网络路径；
- 是否有认证、TLS、审计和退出机制。

不要把“端口能访问”当成“共享服务已经安全”。

## 远程使用前的设计表

~~~text
访问者：
身份认证：
网络范围：
TLS/代理：
允许选择的 workspace：
Provider 凭据归属：
session/log 保存：
管理员：
故障停机：
数据保留：
~~~

如果不能填出这些字段，先保持本机绑定。

## 共享 workspace 的问题

多人共用一个 Web UI 或目录，可能出现：

- 一个 session 读取另一个任务的改动；
- 未提交 diff 被另一个 Agent 当成基线；
- 持久 Shell 继承错误环境；
- 一个任务删除或覆盖另一个任务的文件；
- session 日志混入不同用户输入。

团队任务应按用户、任务或变更请求隔离 workspace，至少用独立 checkout 或分支，并为 session 分配内部关联 ID。

## 共享 Provider 的问题

页面上的模型选择不等于每个用户都有相同权限。确认：

- 凭据由谁提供和轮换；
- Provider 是否记录用户、项目和请求；
- 用户能否添加自定义 endpoint；
- 费用和限流如何归属；
- 共享日志是否包含私有 prompt；
- 任务结束后谁负责清理。

## 远程故障处理

发生异常时，管理员应能：

1. 禁止新任务；
2. 停止正在运行的 Agent 和后台进程；
3. 保留脱敏事件；
4. 检查 workspace 和外部请求；
5. 轮换可能暴露的凭据；
6. 恢复服务前验证默认 profile 和权限。

远程服务必须有明确的关闭路径，不能依赖杀掉一台机器来解决所有问题。
