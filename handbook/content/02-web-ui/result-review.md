# Web 任务结果复核

## 把结果拆成四层

代理交付通常混合了四种信息：

1. **事实**：读取到的文件、命令输出、测试结果；
2. **判断**：对原因、风险或设计的解释；
3. **行动**：已经执行的编辑、命令、安装和网络请求；
4. **承诺**：代理声称接下来可以完成什么。

复核时不要用第四层代替前三层。一个好的交付应该能回答：

~~~text
我看了什么？
我做了什么？
工作区改了什么？
什么命令通过或失败？
还有什么没有确认？
~~~

## 只读任务

检查：

~~~bash
git status --short
git diff --stat
git diff --check
~~~

如果状态为空，说明没有 Git 可见改动，不等于没有读取、网络或临时文件行为。仍要结合工具事件和任务范围判断。

结论应带有文件路径、命令或可重现的观察。不要接受“代码看起来没问题”这种无法回看的结论。

## 写入任务

写入任务至少检查：

- diff 是否只在允许目录；
- 是否意外改变依赖、配置、生成物或锁文件；
- 新增代码是否有对应测试；
- 测试是否真的执行，退出码是否为零；
- 失败测试是否在交付中明说；
- 是否有秘密、私有路径或调试输出进入 diff；
- 是否需要手工回滚或保留迁移脚本。

推荐顺序：

~~~text
git diff --check
→ 读取完整 diff
→ 运行最小相关测试
→ 运行项目级检查
→ 检查依赖和生成物
→ 决定提交或回滚
~~~

## 代理没有提交也不代表安全

Git commit 不是安全边界。代理可以在工作区中写入、删除、生成或执行命令而不提交。提交前后都要检查 diff；如果要让代理提交，要求它先展示范围和验证结果，提交操作仍由人批准。

## 结果报告模板

~~~text
状态：完成 / 部分完成 / 失败 / 需要人工处理

目标：
实际完成：
实际修改：
运行过的命令：
命令结果：
未完成项：
风险：
恢复方式：
~~~

这个模板适用于 Web、headless 和 SDK；它是交付约定，不是 dsh 的原生返回格式。
