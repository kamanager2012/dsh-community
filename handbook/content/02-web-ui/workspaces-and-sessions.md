# Workspace、cwd 与 Session

## 三个位置不能混为一谈

| 名称 | 说明 | 典型检查 |
| --- | --- | --- |
| cwd | dsh 进程启动时的默认目录 | 终端 pwd、启动脚本 |
| workspace | 当前 Agent 被允许处理的项目目录 | Web UI 选择器、文件和 diff |
| session | 一次对话及其事件、模型和恢复状态 | 会话列表、session 日志 |

官方 Web 指南指出，新的 Web UI 在添加 workspace 前不会选中工作区，会话输入框也不可用。这个限制是安全提示：模型没有明确文件上下文时，不应让它开始任务。

## 为什么 workspace 不是一个简单路径

工作区选择影响：

- Agent 读取和编辑哪些文件；
- 相对路径如何解释；
- Shell 的起始目录；
- 任务提示中显示的项目上下文；
- 你最后用 git diff 检查的范围。

但进程可能还会看到 workspace 外的环境、临时目录、挂载、凭据或子进程继承的路径。因此仍然需要沙箱、权限和数据流检查。

## 切换 workspace 的规则

切换项目时，推荐：

1. 先结束或暂停当前 session；
2. 记录当前结果和未完成项；
3. 确认新 workspace 的基线；
4. 新建 session；
5. 重新发送目标、范围和禁止事项。

不要在同一个 session 中把“项目 A 的修复”直接变成“项目 B 的分析”。旧 session 可能保留模型上下文、持久 Shell 和任务假设。

## 页面重载和 session

刷新页面通常不等于重新执行 Agent。能看到历史也不等于运行时已经恢复。遇到页面重载、浏览器关闭或服务重启，重新确认：

- session ID；
- workspace/cwd；
- Provider 和模型；
- profile 和权限；
- 最后一条完成的 turn；
- 是否存在未完成工具调用。

如果当前入口不能明确告诉你这些信息，保守做法是创建新 session，并把已确认的背景写进新任务。

## 多人或多任务并行

在同一台机器上运行多个 Web 任务时：

- 每个任务使用独立 workspace 或明确的目录；
- 记录对应 session；
- 不共享含秘密的 DSH_HOME，除非权限和并发行为已核对；
- 不让不同任务复用带有持久 Shell 的 session；
- 为每个任务保存独立的验收结果。

同一个网页服务里看到多个会话，不代表它们互相隔离了所有进程和文件系统能力。
