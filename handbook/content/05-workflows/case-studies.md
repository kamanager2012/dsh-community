# 工作流案例：把原则落到任务上

下面的案例是可复制的任务设计，不是伪造的运行报告。每个案例都展示目标、边界、工具和验收应该如何组合。

## 案例一：仓库导览

### 目标

为新成员说明目录、主要包、入口和测试。

### 边界

只读当前 checkout，不读秘密、不联网、不安装。工具只需要文件读取和搜索，Shell 只允许运行项目已有的只读命令。

### 验收

- workspace 无 diff；
- 每条主要结论有文件依据；
- 运行过的命令列出退出码；
- 文档、源码、测试冲突单独列出；
- 未运行的命令不写成已运行。

## 案例二：失败测试修复

### 目标

修复一个能复现的单元测试失败。

### 边界

先读和复现，再允许修改 src/ 和对应测试。禁止删测试、升级依赖、联网和提交。每次修改后运行最小测试。

### 验收

- 原失败能够解释；
- diff 在允许目录；
- 相关测试通过；
- 项目级检查没有新的失败；
- 交付中列出未解决问题。

## 案例三：依赖升级

### 目标

升级一个指定依赖并处理兼容性。

### 边界

允许修改 package manifest、锁文件和受影响源码；禁止顺手升级无关依赖。先查 changelog 和现有约束，网络只允许访问批准包源。

### 验收

- lockfile 变更符合目标；
- 构建、类型和测试通过；
- 依赖树没有意外大范围变化；
- 回滚能恢复旧版本；
- 新依赖许可证和安全政策已检查。

## 案例四：文档迁移

### 目标

将旧说明迁移为当前命令和结构。

### 边界

依据官方 README、用户指南和当前源码；旧截图只作为待核对材料。禁止编造运行结果、版本承诺和“已验证”文字。

### 验收

- 命令可由当前版本帮助解释；
- 外链和相对链接可访问；
- 术语统一；
- 没有真实 key、个人路径和虚构日志；
- 旧章节被明确替换或保留原因。

## 案例五：批量只读报告

### 目标

对多个独立仓库输出相同格式的只读报告。

### 边界

每个仓库独立 workspace、session 和日志；不共享可写目录；失败任务不影响其他任务；输出只保留脱敏摘要。

### 验收

- 每个任务有独立状态；
- 退出码和外部检查都记录；
- 遗留进程和临时目录清理；
- 失败原因可区分；
- 不能用总体成功率掩盖单任务失败。
