# 代码修改工作流

## 先把“修复”限定清楚

“让测试通过”可能需要改源码、测试、依赖、配置或环境。交给 Agent 前明确：

- 哪个失败是目标；
- 允许改哪些目录；
- 禁止改哪些文件；
- 是否允许改依赖和锁文件；
- 是否允许联网或安装；
- 测试和回滚命令；
- 失败后保留什么现场。

## 修改任务模板

~~~text
目标：修复 [测试/错误]，保持 [接口/行为] 不变。
workspace：使用当前已选的临时 checkout。
允许修改：src/ 和对应测试目录。
禁止：不改依赖版本，不删除测试，不提交 commit，不访问 workspace 外路径。
步骤：先复现失败，再定位根因，提出最小改动，修改后运行相关测试。
验收：运行 [命令 1]、[命令 2]、git diff --check，并检查完整 diff。
停止：需要扩大目录、联网、安装依赖或提高权限时先询问。
交付：列出修改文件、命令及退出码、未解决风险和回滚方式。
~~~

## 代理修改前

先要求它报告：

- 当前失败是否能复现；
- 相关文件和候选根因；
- 预计修改范围；
- 不会触碰的文件；
- 验收命令。

如果任务一开始就要求编辑，通常说明范围还没有定义好。先读再写可以减少无关 diff。

## 修改中

每次编辑后检查：

- 文件路径是否在允许范围；
- 是替换、插入还是删除；
- 是否改变了接口、配置和错误处理；
- 是否自动生成了格式化或锁文件变更；
- 是否需要立即运行小范围测试。

高影响编辑不要用“一次大 patch”掩盖多个假设。把独立变更分开，让每个变更都有自己的验证。

## 修改后

推荐顺序：

~~~bash
git diff --check
git diff --stat
git diff --name-only
# 先运行最快的相关测试
# 再运行项目级检查
~~~

最后读取完整 diff，尤其检查：

- 测试是否被删掉或放宽；
- 错误是否被吞掉；
- 依赖是否被意外升级；
- 日志是否打印秘密；
- 兼容性是否被破坏；
- 代理是否修改了契约未允许的目录。

## 交付判定

只有满足以下条件才称为完成：

- 目标失败被复现或原因有足够证据；
- 改动在约定范围内；
- 相关验证通过，或失败已明确交付；
- diff 无隐藏生成物；
- 未解决风险被写出；
- 回滚方式可执行。

Agent 的最终回答可以总结这些内容，但不能替代命令和 diff。
