# 文档、重构与大范围变更

## 文档任务也需要范围

文档修改常常比代码更容易扩大，因为模型会主动补充“看起来合理”的说明。任务中写清：

- 面向谁；
- 依据哪些文件；
- 允许修改哪些文档；
- 是否允许改示例和 API 名称；
- 需要保留哪些术语；
- 是否需要中英文同步；
- 链接、代码块和命令怎样检查。

## 文档任务模板

~~~text
目标：将 [主题] 整理成面向 [读者] 的说明。
依据：只使用 [官方页面/源码/当前文件]；不凭空补充未确认的行为。
范围：只修改 docs/指定目录。
要求：保留命令可复制性，区分事实、建议和版本注意。
验收：检查相对链接、代码块、术语一致性和敏感信息；列出引用来源。
禁止：不把未运行的命令写成已验证，不加入真实密钥、私有路径或虚构日志。
~~~

## 重构任务

重构要把“行为不变”写成验收条件：

- 公共接口不变；
- 序列化格式不变；
- 错误类型或消息是否可变；
- 性能边界是否需要保持；
- 测试覆盖是否必须保留；
- 迁移脚本和回滚是否需要。

代理可以先生成迁移图，再分阶段改动。不要让一次任务同时重排文件、改 API、升级依赖和重写测试。

## 术语和版本

官方项目快速迭代时，文档最容易出现“新旧命令混用”。维护文档时在每个重要命令旁边保留：

~~~text
适用入口：
适用版本：
需要的前置：
命令：
预期输出：
失败时检查：
~~~

无法确认某个字段时，明确写“以当前版本帮助为准”，不要用一条旧的截图制造确定感。

## 文档验收

~~~bash
python3 scripts/validate_handbook.py
rg -n "api[_ -]?key|sk-[A-Za-z0-9]" content
~~~

项目自身文档另运行 Markdown lint、链接检查或构建。文档的“完成”包括能被别人阅读、复制、验证和更新，而不只是文字变长。
