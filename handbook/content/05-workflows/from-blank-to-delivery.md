# 主线实战：从空白 workspace 到可验收交付

这是整份手册的主线。它把一次真实的 Agent 任务拆成可以暂停、复核和恢复的阶段：先建立基线，再只读理解，随后做最小修改，最后用外部命令和 diff 验收。

本章是可重复的操作教程，不是已经完成的运行报告。下面的命令、退出码、文件变化和模型表现都需要在你的 checkout 中实际产生；本章不提供伪造日志、截图或“已经成功”的数字。

## 你将完成什么

选择一个可以丢弃或回滚的项目副本，使用一个边界清楚的任务完成以下闭环：

```text
准备环境
  → 建立基线
  → 只读理解项目
  → 写出最小计划
  → 允许有限修改
  → 独立运行验证
  → 检查 diff 与副作用
  → 交付、恢复或停止
```

适合第一次练习的任务：

- 修复一个能够复现的测试失败；
- 给现有模块补一个小功能和对应测试；
- 把一段旧安装说明迁移为当前命令；
- 只读梳理一个陌生仓库并输出文件依据。

不要用生产目录、含客户资料的目录或唯一的未提交工作区作为练习对象。

## 阶段 0：准备可恢复的现场

### 需要先确认

- dsh 能启动，且当前版本的帮助能解释你要用的参数；
- Provider、模型和输入模态已经配置，但没有把密钥值写入任务；
- workspace 是临时 checkout、分支或可恢复副本；
- 你知道项目现有的测试、构建或类型检查入口；
- 任务不依赖未经批准的联网、安装或生产凭据。

### 建立基线

在提交任务前，由人或独立脚本执行：

```bash
node --version
npx @deepseek-ai/dsh --help
git status --short
git diff --stat
```

根据项目实际情况补充测试、构建或类型检查命令。没有运行过的命令不要在交付中写成“已通过”。

把基线填入任务卡：

```text
项目/checkout：
dsh 版本或来源：
Node/Python 版本：
Provider/模型：
workspace：
初始 git status：
初始测试/构建结果：
当前允许联网：是 / 否 / 仅限 [范围]
```

## 阶段 1：只读理解，不急着改

先用 Web UI 或 Headless CLI 提交只读任务。第一轮的目的，是确认 workspace、工具和模型真的在同一个现场工作，而不是证明模型能写代码。

### 可复制的只读任务

```text
目标：说明当前仓库的技术栈、入口、主要模块、测试命令和与本任务最相关的文件。
范围：只读取当前选中的 workspace；优先读取 README、包管理文件、入口文件和相关测试。
禁止：不要创建、修改或删除文件；不要安装依赖；不要联网；不要访问 workspace 之外的路径。
要求：每条重要结论列出文件路径；把观察、推断和不确定项分开。
停止：如果需要写入、安装、联网、凭据或扩大路径范围，先停下来询问。
交付：输出项目地图、候选文件、测试入口、风险和下一步建议。
```

### 人工检查点

任务结束后先看外部状态：

```bash
git status --short
git diff --stat
```

然后核对：

- 页面或 CLI 显示的 workspace 是否正确；
- Agent 引用的路径是否存在；
- 工具调用是否真的只读；
- 是否发生了安装、联网、后台进程或文件变化；
- 结论是否区分了事实和推断。

只读任务出现未预期 diff 时，不要立即清理现场。先保留状态，查明是哪个工具、钩子或外部进程产生了变化。

## 阶段 2：把需求收敛成最小计划

把阶段 1 的发现转成一个小而可验收的修改目标。计划必须先回答“改什么”和“不改什么”，再讨论实现方式。

```text
目标：修复 [可复现失败] / 增加 [单一功能] / 迁移 [单一文档路径]。
允许修改：
- [目录或文件 1]
- [目录或文件 2]
禁止修改：
- 依赖版本和锁文件，除非本任务明确允许；
- 无关模块、测试断言和发布配置；
- workspace 之外的路径。
不变量：保持 [公共接口/数据格式/现有行为] 不变。
步骤：先复现或读取基线；提出最小改动；修改后运行相关检查。
验收：[命令 1]、[命令 2]、git diff --check 和人工 diff 复核。
停止：需要扩大文件范围、联网、安装、高权限或无法解释的生成物时先停。
```

如果 Agent 直接开始修改而没有说明候选文件、根因和验收，暂停任务，让它先输出计划。计划不是完成结果，也不能替代审批。

## 阶段 3：只授权最小修改

确认计划后，开启写入或批准必要的编辑动作。不要因为第一轮只读成功，就自动把权限扩大到全目录、全网络或全凭据。

### 修改任务模板

```text
按已确认的计划实施最小修改。
允许范围：[明确文件/目录]
不允许：删除测试、降低断言、升级无关依赖、修改范围外文件、提交 commit。
每次独立修改后：说明改变了什么，以及下一条验证命令。
如果验证失败：保留失败现场，说明失败发生在哪一步，不要用文字覆盖失败。
完成标准：修改在允许范围内，相关检查已运行，完整 diff 可解释，剩余风险已列出。
```

### 修改中的人工检查点

每次批准前确认：

- 动作的路径仍然在允许范围；
- 是否产生锁文件、构建物、缓存或临时文件；
- 是否引入新的网络请求、凭据读取或后台进程；
- 代码变化是否仍然服务于原目标；
- 失败时是否可以回到上一个检查点。

大型任务不要把所有编辑合并成一个不可解释的 patch。把独立变化拆开，让每一组变化都有自己的验证。

## 阶段 4：用外部检查验收

验收顺序应当从便宜、局部、可解释的检查开始，再扩大到项目级检查：

```bash
git diff --check
git diff --stat
git diff --name-only
# 运行项目已有的最小相关测试
# 再按项目需要运行类型检查、构建或完整测试
git status --short
```

不要把任务最后一句话当成验收结果。至少把以下事实分开记录：

| 事实 | 由什么证明 | 不能用什么替代 |
| --- | --- | --- |
| 改了哪些文件 | `git diff --name-only` 和完整 diff | Agent 的文件列表 |
| 测试是否通过 | 实际命令、退出码和输出 | “测试应该没问题” |
| 是否有越界改动 | diff、状态和路径检查 | 任务文本里的承诺 |
| 是否引入依赖或生成物 | manifest、lockfile、状态和 diff | 最终摘要 |
| 是否满足业务要求 | 人工检查或独立验收器 | 模型自评 |

如果命令失败，不要为了得到绿色结果删除测试、降低断言或改写失败描述。把失败原因、已尝试动作和下一步建议交给人工处理。

## 阶段 5：交付或恢复

### 可交付的最小报告

```text
状态：完成 / 有条件完成 / 未完成 / 需人工介入
目标：
实际修改文件：
未修改但检查过的关键文件：
根因或设计取舍：
运行过的命令与退出码：
外部验收结果：
未解决问题：
安全/数据流注意：
回滚方式：
session 或检查点引用：
```

“完成”只能在目标、范围、外部检查和人工验收都满足时使用。测试通过但 diff 越界，应当是“需人工介入”；代码改对但项目级检查未运行，应当是“有条件完成”，而不是伪装成全绿。

### 失败恢复顺序

1. 停止正在运行的 Agent、Shell 和后台进程；
2. 保存当前状态、diff、日志引用和最后一条可靠命令；
3. 确认 workspace、session、模型、权限和任务目标；
4. 回到最近一个可解释的检查点；
5. 选择继续、fork、新 session 或回滚；
6. 重新运行最小验证，再决定是否扩大范围。

如果无法确认旧 session 是否带着错误上下文，优先新建 session，重新提交脱敏后的目标和基线，不要只复制一个 session ID。

## 同一条主线的三个入口

| 入口 | 适合什么时候用 | 入口说明 |
| --- | --- | --- |
| Web UI | 第一次使用、需要逐步审批和观察工具时间线 | [Web UI 首次任务](../02-web-ui/first-run.md) |
| Headless CLI | 任务边界固定、需要脚本捕获退出码 | [Headless CLI](../automation/headless-cli.md) |
| Python SDK | 需要在程序中管理 session、结果和清理 | [SDK 工程实践](../08-automation/sdk-engineering.md) |

入口可以不同，但五个检查点不能省略：任务契约、权限边界、能力配置、状态记录、外部验收。

## 主线完成标准

走完本章后，不要求你证明模型在所有项目上都可靠；要求你能真实完成并说明下面这些事情：

- [ ] 在可恢复 workspace 中建立了基线；
- [ ] 用只读任务确认了路径、工具和模型；
- [ ] 把目标、范围、不变量、权限、验收和停止条件写清楚；
- [ ] 每次修改都能对应到一个允许范围和检查点；
- [ ] 由外部命令、diff 或人工检查证明实际结果；
- [ ] 失败时能保留现场并选择继续、恢复或停止；
- [ ] 交付报告区分了事实、推断、未运行检查和剩余风险。
