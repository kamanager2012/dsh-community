# 长任务与阶段交付

## 为什么要分阶段

长任务的风险不是只有模型上下文变长，还包括：

- 工作区累积了无法解释的 diff；
- session 带着过时的目标；
- 模型、Provider 或权限改变；
- 某个中间命令失败却被继续掩盖；
- 任务最后只剩一句无法验证的总结。

因此把长任务写成阶段，而不是一个无限大的 prompt。

## 阶段模板

~~~text
总目标：
阶段 1：理解和基线
  交付：
  验收：
  停止：
阶段 2：最小改动
  交付：
  验收：
  停止：
阶段 3：测试和修复
  交付：
  验收：
  停止：
阶段 4：整理和交付
  交付：
  验收：
  停止：
恢复点：
~~~

每个阶段结束都记录当前 diff、测试结果、未完成项和下一步假设。

## 何时继续同一个 session

继续原 session 适合：

- 目标没有变化；
- workspace 没有被其他任务修改；
- 模型和权限仍然正确；
- 前一阶段留下的背景仍然有效；
- 能知道最后一个完成的 turn。

下列情况更适合新建 session：

- 任务目标改变；
- Provider 或模型改变；
- 工作区换了；
- 旧 session 中有错误或敏感内容；
- 需要清空错误的图片或工具上下文；
- 无法确认恢复是否真的发生。

## 检查点内容

~~~text
时间：
任务阶段：
workspace：
session：
模型/Provider：
权限：
已完成：
当前 diff：
已通过测试：
未完成：
下一步：
回滚：
~~~

不要把完整日志复制到公共工单。保存脱敏摘要和内部受控引用。

## 失败恢复

恢复的顺序是：

1. 停止正在运行的进程和后台任务；
2. 保存工作区状态；
3. 读取最后一个可靠检查点；
4. 确认 session、workspace、模型和权限；
5. 重新运行最小验证；
6. 决定继续、fork 或从新 session 重述目标。

恢复失败时明确报告失败，不要静默新建 session 并让交付看起来像连续完成。
