# 只读分析工作流

## 适用场景

只读任务适合第一次接触仓库、做架构摸底、整理测试入口、审查配置和准备后续修复。它的成功标准不是回答长，而是：

- 工作区没有未预期改动；
- 结论能回到文件或命令；
- 观察和推断分开；
- 需要写入或扩大范围时会停止。

## 任务模板

~~~text
目标：分析当前项目的目录结构、主要模块、运行入口和测试入口。
范围：只读取当前 workspace。
禁止：不要创建、修改、删除文件；不要安装依赖；不要联网；不要访问 workspace 之外的路径；不要读取凭据文件。
方法：先列目录和入口文件，再读取与目标相关的配置、源码和测试。
输出：按“事实、推断、不确定项”分组，并列出文件路径和命令。
完成标准：给出可以由我复查的结论，workspace 保持无 diff。
停止：需要写入、安装、联网、读取排除文件或提高权限时先停下来询问。
~~~

## 推荐观察顺序

1. 顶层目录和版本控制状态；
2. README、贡献指南和项目入口；
3. package/pyproject/go.mod 等构建配置；
4. 测试脚本和 CI；
5. 与问题直接相关的源码；
6. 文档与源码之间的差异。

不要让模型一开始遍历整个家目录或扫描所有二进制。先从项目索引文件开始，按证据扩展。

## 结论格式

~~~text
事实：
- 文件 X 声明了……
- 命令 Y 返回……

推断：
- 这可能意味着……

不确定：
- 还没有运行……
- 文档和源码在……处不一致

建议的下一步：
- 需要谁批准什么；
- 应该运行哪条只读命令；
- 如果允许写入，范围是什么。
~~~

## 只读验收

在任务前后执行：

~~~bash
git status --short
git diff --stat
git diff --check
~~~

如果项目不是 Git 仓库，使用文件清单、哈希或临时副本比较。只读任务不等于不能执行命令；关键是命令是否会写入缓存、生成物、锁文件或临时目录。
