# 复核与验收设计

## 验收不是最后加一句“请确认”

验收应该在任务开始前写入契约，并由 Agent 之外的命令、测试或人工步骤执行。好的验收具备：

- 可观察；
- 可重复；
- 与目标直接相关；
- 失败时能定位；
- 不依赖模型自报。

## 三类验收

### 机器验收

测试、构建、类型检查、lint、schema 校验、git diff --check 和文件哈希。适合确定性要求高的部分。

### 结构验收

检查文件范围、依赖变化、配置字段、API 兼容、日志和生成物。适合防止任务“完成了功能但扩大了范围”。

### 人工验收

检查设计取舍、用户体验、隐私、业务语义和无法自动表达的风险。人工验收不应该只是阅读代理最终回答，而是阅读实际 diff、结果和约束。

## 阶段验收表

| 阶段 | 输入 | 检查 | 通过标准 |
| --- | --- | --- | --- |
| 理解 | 任务和 workspace | 范围、基线 | 能说清不变量 |
| 计划 | 方案 | 影响面、权限 | 动作可回滚 |
| 修改 | diff | 文件和依赖 | 在允许范围 |
| 测试 | 命令 | 退出码、日志 | 相关检查通过 |
| 交付 | 报告 | 完成/未完成 | 风险和恢复明确 |

## 失败状态

推荐至少区分：

- completed：目标和外部验收都通过；
- partial：部分目标完成，有明确剩余；
- failed：关键步骤失败；
- blocked：缺少凭据、权限、环境或人工决定；
- needs-review：自动检查通过但需要业务判断。

不要把 blocked 改写成 completed。状态准确比报告好看更重要。

## 复核清单

~~~bash
git status --short
git diff --name-only
git diff --stat
git diff --check
~~~

再执行项目相关检查。对于非 Git workspace，使用清单、哈希和临时副本。
