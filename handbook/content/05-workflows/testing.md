# 测试与失败定位

## 不要把测试当成一句命令

测试工作流至少包含四个问题：

1. 哪个失败是真正的问题；
2. 失败是否可重复；
3. 修改是否解决根因而不是隐藏症状；
4. 其他检查是否仍然通过。

Agent 可以帮助运行命令和解释输出，但外层验收必须保留退出码和原始失败摘要。

## 测试任务模板

~~~text
目标：定位 [命令] 失败的根因，并在允许范围内修复。
第一步：先运行失败命令，不要修改文件。
范围：允许读取项目；允许修改 [目录]。
禁止：不删除或跳过测试，不降低断言，不改变依赖版本。
验证：先运行最小相关测试，再运行 [项目级检查]。
输出：失败复现、根因、修改、命令结果、未解决问题。
停止：测试涉及外部服务、密钥、破坏性数据或需要新增依赖时先询问。
~~~

## 按失败层级定位

~~~text
命令未找到
  → 环境/脚本层

解析或编译失败
  → 依赖、配置、类型或语法层

单测失败
  → 逻辑、fixture、时间或状态层

集成测试失败
  → 服务、网络、数据库或进程边界

端到端失败
  → 浏览器、凭据、外部端点或时序层
~~~

先处理最接近根因的一层，不要看到端到端失败就让 Agent 重写业务代码。

## 证据顺序

保存：

- 运行命令；
- 工作目录；
- 环境版本；
- 退出码；
- 首个有意义的错误；
- 相关日志位置；
- 修改前后 diff；
- 重跑结果。

日志可以脱敏，但不要只保留最后一句“failed”。没有首个错误和命令上下文，后续重试很难比较。

## 测试不通过时的交付

如果修改后的测试仍失败，报告必须说：

~~~text
已修复：
仍失败：
失败命令：
首个错误：
已排除：
未确认：
下一步：
~~~

不要为了让 Agent 得出 completed 而要求它“把测试修到绿”。正确状态可能是失败、部分完成或需要人工处理。
