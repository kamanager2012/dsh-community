# 权限、审批与沙箱

## 权限策略不是沙箱

权限策略决定 Agent 的请求是否需要批准、允许或拒绝。沙箱决定进程实际能读写什么。workspace 决定任务面向哪个项目。三者叠加但不互相替代。

~~~text
权限策略 → 请求能否通过
沙箱     → 进程能访问什么
workspace → 任务应处理什么
人工验收 → 结果是否真的合规
~~~

官方配置中常见 read-only、workspace-write 和 danger-full-access 等预设，但具体默认值和字段随版本、profile 和组合变化。升级后用当前版本的配置导出确认，不要把某版默认值写成永久承诺。

## 权限梯度

| 等级 | 用途 | 适合的动作 |
| --- | --- | --- |
| read-only | 初次摸底、审查和报告 | 读取文件、搜索、解释配置 |
| workspace-write | 临时 checkout 中的小范围修改 | 编辑指定目录、运行测试 |
| 高权限/全访问 | 隔离容器中的特殊任务 | 明确批准的系统级动作 |
| 生产权限 | 不建议直接交给 Agent | 需要额外组织审批和人工执行 |

权限越高，任务文本越不能含糊。高权限不是“让模型更聪明”的办法，只是扩大了它能做的事情。

## 审批策略

批准一个动作前检查：

- 目标路径；
- 命令和参数；
- 是否有 shell 展开；
- 是否会联网、安装、上传或删除；
- 是否包含凭据或私有数据；
- 如何回滚和验证。

不要因为任务已经批准过一次，就把后续所有动作视为自动批准。每个动作都可能改变范围。

## 沙箱与进程可见性

读取、网络访问、进程可见性和文件写入不是一条轴：

- 可以限制写入，但仍允许读取过多文件；
- 可以限制 workspace，却让子进程访问环境变量；
- 可以阻止网络，却让日志包含敏感内容；
- 可以要求审批，却让已批准的命令展开到更大范围。

为 Shell、PTY、子 Agent、MCP 和插件分别确认实际边界。

## 权限变更后的 session

General settings 或环境变量改变权限后，不要假设已经打开的 session 自动采用新策略。新建 session，重新记录模型、workspace 和权限。旧 session 如果拥有持久 Shell，还可能带着旧环境。

## 可执行的权限检查

任务前：

~~~bash
npx @deepseek-ai/dsh --profile web --dump-config
git status --short
~~~

任务中：观察审批、工具、进程和网络请求。任务后：检查 diff、测试、生成物和日志。
