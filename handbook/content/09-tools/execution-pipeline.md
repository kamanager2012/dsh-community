# 工具执行流水线

## 一次工具调用发生了什么

可以把调用抽象成：

~~~text
模型产生 tool/call
  → 参数 schema 校验
  → tools/pre-execute
  → 权限/审批/策略
  → tools/execute
  → 文件、Shell、进程或外部服务
  → tools/post-execute
  → tool/result
  → session 记录
  → 模型决定下一步
~~~

不同版本会有更多事件或不同命名，但定位问题时要分清“模型提出了调用”和“工具真的执行了”。

## 前置门禁

工具执行前可能发生：

- 参数格式校验；
- 当前 agent scope 检查；
- 观察策略；
- 审批询问；
- 沙箱包装；
- Provider 或能力限制；
- 用户拒绝；
- 任务取消。

如果调用在前置阶段被拒绝，通常不会有文件或进程结果。报告中应说明拒绝发生在哪一层。

## 执行结果

执行后检查：

- 退出码；
- stdout/stderr；
- 文件是否真正改变；
- 进程是否仍在运行；
- 结果是否被截断；
- 是否产生 session 事件；
- 是否触发了外部网络；
- 是否有后续工具动作。

“tool/result 返回了”只说明 dsh 收到结果，不一定说明结果满足任务目标。

## 后置策略

后置策略可能：

- 脱敏结果；
- 限制输出大小；
- 记录观察事件；
- 将后台任务加入 job registry；
- 改写错误；
- 触发下一轮 Agent 输入。

因此直接调用底层工具和通过 dsh 工具层调用不是一回事。插件作者要遵守现有 seam；使用者只应依赖公开工具和当前版本文档。

## 取消

取消工具调用时，分别确认：

- 模型轮次是否停止；
- Shell 子进程是否停止；
- 后台 job 是否停止；
- 文件半成品是否存在；
- session 是否记录取消；
- 外部请求是否已经发出。

取消请求不能撤销已经发出的网络请求或已经写入的文件。
