# 扩展 Cookbook：从需求到插件

## 先写能力说明

在写代码前填：

~~~text
能力名称：
用户/模型如何触发：
输入：
输出：
依赖的 context service：
监听的事件：
会读取什么：
会写入什么：
会联网吗：
需要什么权限：
如何取消：
如何清理：
如何验收：
~~~

这份说明先于实现。它可以暴露“其实只需要一个脚本”或“数据流还没被批准”的问题。

## 添加面向模型的工具

步骤：

1. 找到 ctx.tools 的现有注册模式；
2. 定义稳定名称和严格 schema；
3. 写清成功、失败和取消；
4. 把高影响动作放进工具流水线；
5. 增加权限/审批边界；
6. 输出脱敏且可观察；
7. 写插件卸载和资源释放；
8. 在最小 profile 中运行；
9. 更新工具目录和用户文档。

不要把一个工具的“默认成功”写成系统安全保证。工具可以被错误参数、端点、进程和数据影响。

## 添加 LLM Provider

Provider 的实现分为：

~~~text
配置 → 凭据 → 模型目录 → 请求编码
  → streaming → tool call → multimodal
  → 错误 → 取消 → 日志脱敏
~~~

先选择最接近的现有适配器，列出协议差异。每个差异都要有配置说明和错误路径。不要为了让一个端点通过示例任务而静默丢弃 tool call 或 reasoning 字段。

## 添加会话状态

模型可见的新状态必须能从 session 日志派生和重放。设计时回答：

- 事件名称和 schema；
- 追加时机；
- history 如何投影；
- resume/fork 如何处理；
- 迁移旧日志的方式；
- 错误如何恢复；
- 脱敏和保留策略。

只在内存中保存会造成刷新、fork、恢复和 UI 不一致。

## 添加事件策略

先查事件的 dispatch mode：

- emit：观察；
- waterfall：包装或短路；
- parallel：并行观察；
- serial：按序决策。

只在拥有决策权时短路 waterfall。策略插件要明确是拒绝、改写、记录还是转发，避免监听器之间互相覆盖。

## 添加 UI 节点

UI 节点要把运行时状态与用户操作分开：

- 显示当前 session、workspace 和权限；
- 对危险动作提供明确上下文；
- 表单字段与配置 schema 一致；
- 失败和取消可见；
- 长任务有进度和停止入口；
- 不在前端回显密钥。

## 完成定义

插件完成至少意味着：

- 最小 profile 可加载；
- 工具/schema/Provider 行为有文档；
- 权限和数据流已说明；
- 资源能 teardown；
- 失败不会静默扩大范围；
- 兼容版本和回滚写清；
- 用户能判断是否应该安装。
