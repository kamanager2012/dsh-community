# Profile、Bundle 与 Patch 设计

## 三种分发对象

| 对象 | 作用 | 适合 |
| --- | --- | --- |
| profile | 一个可启动的具名组合 | web、headless、团队运行方式 |
| bundle | 可分发的插件配置层 | 复用一组服务和默认值 |
| patch | 对当前配置树做替换或插入 | 项目/环境差异 |

不要把 patch 当作永久配置的唯一来源。复杂组织应保留“基础 bundle、环境 patch、临时 overlay”的层级。

## Patch 的风险

Patch 可能按 ID 替换整个配置。如果只想改一个字段，却复制了一份旧 config，后续上游增加字段时，旧 patch 可能把新字段覆盖掉。

安全做法：

1. 导出当前配置；
2. 只修改必要条目；
3. 用新 profile 或临时 DSH_HOME 测试；
4. 对比 dump-config；
5. 运行低风险任务；
6. 记录回滚方式。

## 团队 profile

团队 profile 要有：

~~~text
用途和读者：
组合层级：
工具白名单：
权限/审批：
Provider：
session 和日志：
网络：
升级策略：
owner：
~~~

把这个说明和配置放在同一个受控仓库。不要把凭据和个人路径写进去。

## 临时 overlay

临时 overlay 适合一次排错或局部实验，但要：

- 使用明确文件；
- 任务结束删除；
- 不默认启用高权限；
- 记录谁批准；
- 不提交带秘密的值；
- 将结果与基础 profile 分开比较。

## 发布插件前

先在干净 DSH_HOME 中安装/加载，检查：

- profile 是否能启动；
- 工具目录是否符合预期；
- teardown 是否释放资源；
- 旧插件不存在时是否能报清楚；
- patch 不适用时是否安全失败；
- 版本升级后的兼容性。
