# 任务契约：让“完成”可以被检查

“修一下这个问题”“看看代码有没有问题”“跑一下测试”都缺少完成定义。模型可能给出听起来合理的回答，却没有完成真正需要的结果；也可能为了追求结果越过工作区、权限或数据边界。

任务至少写清六件事：目标、范围、不变量、验收、停止条件和恢复点。这是本手册的工程模板，不是 dsh 原生的 YAML 配置格式。

## 最小模板

```yaml
task:
  goal: "用一句话描述最终要交付的结果"
  scope:
    workspace: "明确的目录或仓库"
    allowed_paths:
      - "src/"
      - "tests/"
    external_services: []
  invariants:
    - "不修改接口兼容性"
    - "不提交凭据和生成物"
  acceptance:
    checks:
      - "运行指定测试命令"
      - "检查 diff 和格式"
    deliver:
      - "命令结果"
      - "变更摘要"
  stop_conditions:
    - "需要访问 workspace 之外的路径"
    - "需要安装依赖或启用更高权限"
    - "验证命令失败且原因未定位"
  recovery:
    checkpoint: "最后一个已确认的步骤"
    resume_or_fork: "说明何时继续原 session、何时新建 session"
```

不需要真的把这段 YAML 交给 dsh；把它翻译成任务文本即可。

## 五个检查点

### 1. 范围

开始前确认：

- 当前 workspace 是否正确；
- 允许读、写、执行和联网到什么程度；
- 工作区有哪些未提交改动；
- 是否需要第三方 Provider、MCP 或插件；
- 哪些目录和数据绝不能触碰。

### 2. 计划

要求代理先说清楚：

- 它打算先观察什么；
- 哪一步可能修改文件或访问网络；
- 需要哪些工具和权限；
- 如何证明目标完成。

计划只是计划。后续工具调用、实际 diff 和命令输出才是结果。

### 3. 行动

每次高影响行动前检查：

- 是否仍在契约范围内；
- 是否触发审批；
- 参数是否包含外部输入、秘密或不可逆操作；
- 是否应该先创建 checkpoint。

### 4. 验收

至少包含一种外部可观察的检查：测试、构建、类型检查、diff、文件哈希、HTTP 状态或人工复核。代理的最终文字不能单独作为验收依据。

### 5. 交付

交付时要求回答：

```text
做了什么：
没有做什么：
实际改动：
验证命令和结果：
剩余风险：
恢复或回滚方式：
```

如果验证失败，状态应写成“失败”“部分完成”或“待人工处理”，不能为了让流程看起来完整而改写成成功。

## 任务类型示例

### 只读分析

```text
目标：找出测试入口和可能的失败原因。
范围：只读取当前 workspace。
禁止：不写文件、不安装依赖、不联网。
完成标准：列出检查过的文件、运行过的只读命令和不确定项。
```

### 代码修改

```text
目标：修复指定测试失败。
范围：只允许修改 src/ 和对应测试。
禁止：不改依赖版本、不删除测试、不提交 commit。
验收：运行测试、git diff --check，并总结变更。
停止：需要扩大范围或提高权限时先询问。
```

### 长任务或恢复任务

```text
目标：分阶段完成迁移。
检查点：每阶段结束记录已完成项、剩余项和当前 diff。
恢复：恢复前先确认 session、workspace、模型和权限仍然正确。
交付：列出每个阶段的命令结果和未完成风险。
```

## 任务契约不是替代品

契约不能替代权限配置、审批、沙箱或人工复核。它的作用是让这些边界在任务开始前写明白，并在任务结束后有可检查的完成标准。
