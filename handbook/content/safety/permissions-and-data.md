# 权限、沙箱与数据边界

安全使用 dsh 的顺序是：先限制行动空间，再扩大能力；先确认数据流，再允许不可逆操作。

## 三层边界

```text
权限策略：哪些行动需要批准
       ↓
沙箱：进程实际能访问和修改什么
       ↓
外部服务：模型、搜索、MCP、插件或网关会收到什么
```

三者不是一回事。审批通过不等于数据可以离开本机；workspace-write 也不等于工作区中的所有文件都适合交给代理。

具体版本的权限预设和默认值可能变化。升级或切换配置后，先查看当前版本的帮助、配置导出和 General settings；不要把某一版的默认值当成永久契约。

## 推荐权限梯度

| 场景 | 推荐边界 | 允许的第一步 |
| --- | --- | --- |
| 初次体验 | read-only 或保持审批 | 读取结构、定位测试、解释配置 |
| 小范围修改 | workspace-write + 高风险操作审批 | 先生成计划，再改指定目录 |
| 自动化 CI | 隔离容器/临时 checkout + 工具白名单 | 只运行定义好的任务和验收器 |
| danger-full-access | 仅可丢弃容器或专门沙箱 | 不用于未知仓库、个人主机或生产环境 |

如果当前界面无法确认有效权限，先暂停，不要为了让任务继续而直接切到最高权限。

## workspace 不是全部安全边界

任务前后检查：

```bash
git status --short
git diff --stat
```

同时确认：

- workspace 是否包含 `.env`、私钥、生产配置或客户数据；
- 工具是否能访问 workspace 外的临时目录；
- Bash、PTY、子 Agent 和插件是否继承更大的进程可见范围；
- 文件内容、命令参数或工具结果是否会发给外部模型。

读取权限、网络权限和进程可见性不能简单等同为“文件修改权限”；配置沙箱时要分别考虑这些维度。

## 凭据处理

- key 通过 UI 的凭据存储或环境变量引用；
- 仓库中只保留变量名和脱敏 Provider 配置；
- 命令输出、session 日志、截图和错误报告都要扫描 token、Cookie、Authorization header 和私有路径；
- 共享 `$DSH_HOME` 前确认凭据文件权限；
- 更换 Provider 或端点时，废弃旧凭据，不把旧 key 留在历史 session 和日志里。

不要在示例中放任何看起来可用的真实 key。凭据前缀和完整值都应被扫描并拒绝进入正文、日志和截图。

## 开启网络前的检查

每次开启模型目录、搜索、MCP 或外部插件前，先回答：

1. 哪些输入会发送到哪个 Provider；
2. 是否包含私有代码、路径、凭据、客户数据或内部提示；
3. 工具结果和 session 日志保存在哪里；
4. 是否启用遥测，collector 地址是什么；
5. 外部服务的保留、训练、访问和删除政策是什么；
6. 任务完成后如何清理临时数据和凭据引用。

具体 Provider、MCP、插件和公司网关可能有额外政策，不能用“dsh 本地运行”概括整个数据流。可继续阅读[官方隐私说明](https://deepseek.com/harness/privacy/)和[官方数据处理说明](https://deepseek.com/harness/data-processing/)。

## 发生风险时

```text
暂停会话
  → 拒绝当前审批或停止进程
  → 保留脱敏事件和时间线
  → 检查 workspace diff、凭据和外部请求
  → 必要时撤销或轮换凭据
  → 从干净 checkout 重建
```

不要先删除日志再判断发生了什么，也不要把一次模型拒绝当成完整安全控制。
